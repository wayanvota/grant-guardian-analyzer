# Grant Guardian: documentation review and recommended changes

Research date: September 29, 2026. Comparison baseline: Wayan's February 26–28, 2026 build and the currently served application at https://wayan.com/grant-guardian-analyzer.html.

## Judgment

Improve the existing simulator before expanding it. The strongest immediate work is correcting misleading provenance, inaccurate Form 990 references, and incomplete-data scoring. The three-ratio educational concept remains consistent with PJMF's public examples. This review did not establish a newly published, universal PJMF scoring algorithm that could replace the simulator's assumptions.

This review preceded the v2 implementation. See the repository CHANGELOG for the subsequent fixes. No public-site deployment was performed. The preserved source is `archive/2026-09-29-live.html`; `docs/behavior-evidence.json` records targeted checks against that historical source using an in-memory DOM stub rather than a full browser test.

## What the search established

1. **Current public product website.** The production [Grant Guardian site](https://gg.mcgovern.org/) says it serves more than 400 organizations and is free for verified U.S.-based philanthropic institutions. I read the rendered production page, not just a search result or staging site. The page has no release date establishing when these statements changed. Adoption is not evidence of accuracy or nonprofit benefit.
2. **Current official FAQ.** [PJMF's product documentation](https://www.mcgovern.org/our-work/data-solutions/grant-guardian/) still names current ratio, cash reserve ratio, and donor-restricted net assets ratio as examples. Funders configure indicators, thresholds, and weights. It publishes current-ratio examples of 1.0 and 0.5; I found no support there for the simulator's exact weights, restriction thresholds, scoring curves, or overall rating bands. The FAQ names Claude 3.7 and 4.0, but it is not a dated deployment record. Avoid asserting that these are the models running today.
3. **Genuinely later discussion, not a feature release.** TAG's [April 1, 2026 account of its NTC session](https://www.tagtech.org/2026/04/reimagining-grant-applications-in-the-age-of-genai/) discusses Grant Guardian and applicant-centered transparency. It does not announce a new Grant Guardian algorithm or integration.
4. **Older documentation worth incorporating.** PJMF's [March 27, 2025 development account](https://medium.com/patrick-j-mcgovern-foundation/social-responsibility-comes-first-product-development-lessons-from-grant-guardian-3c5fe6916019) describes review/edit of extracted values, document/page references, calculation explanations, currency conversion, accessibility, and testing with data from 121 organizations. These features predate the February build; they should not be described as new releases. The article describes a testing process, not a public accuracy benchmark sufficient to validate this simulator.
5. **Technical background for a later extraction feature.** PJMF's [October 28, 2024 engineering article](https://medium.com/patrick-j-mcgovern-foundation/using-ai-for-data-extraction-an-exploration-of-two-techniques-4affd6681c5f) explains why its team chose full-document context over retrieval-augmented generation during development. It is historical design evidence, not proof of today's architecture.
6. **Date traps.** An [AImpactful interview](https://aimpactful.com/grant-guardian-responsible-ai-for-grantmakers-and-nonprofits/) has a February 23, 2026 publication date and later modification metadata. A [PJMF engineer's conference deck](https://assets.swoogo.com/uploads/5895861-68dbeaca2a9a5.pdf) is internally dated October 7, 2025 despite a more recent search-engine date. Neither establishes a post-build feature release.

Search scope included the production website, PJMF website and blog, Learning Hub, Anthropic case study, public interviews, conference materials, and dated 2026 coverage. I did not find a public release history, complete scoring specification, or API documentation in the sources reviewed. That is a bounded search result, not proof that none exists. Authenticated workflows were not inspected. The linked video playlist and a Nationswell PDF could not be fully retrieved; no conclusions depend on their unseen contents. Unrelated products using the same Grant Guardian name were excluded.

## Changes to make before promoting the tool again

### 1. Correct the Form 990 reference map

The current source's docRefs object and form helper text contain substantive errors. Compare against the official [2025 Form 990](https://www.irs.gov/pub/irs-pdf/f990.pdf), Parts VIII and X:

| Current tool reference | Actual form entry | Required correction |
| --- | --- | --- |
| Government grants: Part VIII 1c + 2 | 1c is fundraising events; government grants classified as contributions are 1e | Separate grant contributions from contractual program-service revenue; do not assume all line 2 revenue is government contracts. |
| Foundation/private grants: Part VIII 1b | 1b is membership dues | Request supporting revenue records; do not present this line as a foundation-grant total. |
| Individual contributions: Part VIII 1a | 1a is federated campaigns | Request supporting records instead of pretending the form isolates all individual giving here. |
| Liquid investments: Part X 3–4 | 3 is pledges/grants receivable; 4 is accounts receivable | Use investment schedules and verify liquidity and donor restrictions. |
| Donor-restricted net assets: Part X 28–29 | 28 is net assets with donor restrictions; 29 belongs to the alternative reporting section | Use line 28 where applicable and the appropriate supporting statements. |

Make references conditional on form year and accounting presentation. Cash balances alone do not establish the unrestricted amount. Permit unknown values when supporting detail is absent. These errors can contaminate otherwise correct ratio arithmetic.

### 2. Stop turning missing information into a financial judgment

The numeric helper converts blanks to zero. Undefined ratios receive a component score of 50. In a reproduced check, entering only assets of 100,000 and liabilities of 20,000 returned 63/100, despite no cash, expenses, or restricted-net-asset data. Missing restricted assets became 0.0%.

Represent unknown separately from zero. Show which ratios can be calculated. Suppress the composite when required inputs are incomplete. Require explicit confirmation of true zero values where material. A second check returned 80/100 and “Adequate Financial Health” for a case with assets of 100,000 and liabilities of 120,000. Display nonpositive total net assets prominently and explain why the restriction ratio is not interpretable in the ordinary way. Do not infer a funding decision from that condition.

### 3. Repair and document scoring behavior

With a restriction threshold of 90%, the component formula returns 52.94 at a restriction ratio of 130%, then rises to 105.88 at 160%. This violates the intended direction and scale. A ratio over 100% can arise when unrestricted net assets are negative, so simply hiding the case would lose useful information.

Specify meaningful behavior for zero thresholds, zero denominators, negative net assets, out-of-range entries, and incompatible totals. Ensure each component stays within its intended range and changes in the intended direction. Enforce valid individual weights and a total of 100. Add regression tests for these cases before release.

### 4. Label the simulator's assumptions and outputs accurately

Replace “AI Extracted” with “Manually entered” and “AI-Generated Financial Narrative Summary” with “Rule-based financial summary.” The current implementation calls no model and parses no documents. Rename “Extracted Data Log” accordingly.

Put an independence statement next to the headline and on printed reports. Identify each parameter as a published PJMF example, a user-entered funder setting, or a simulator assumption. The educational value is exploring documented indicators under explicit assumptions; the tool cannot establish what a specific foundation will see without its configuration.

### 5. Make verification real

Step 5 tells users to edit values but renders ordinary table cells without editing controls. Add an edit action, actual document title/year/page fields, and a confirmation state for each material input. Carry those references and corrections into the report. A generic label such as “Balance Sheet, Current Assets section” is guidance, not a citation to the user's evidence. Reconcile total assets minus liabilities against restricted plus unrestricted net assets where the accounting presentation supports it.

## Improvements after those corrections

### 6. Show scenario sensitivity instead of emphasizing a universal score

Put the three raw ratios and data completeness ahead of the overall score. Let users compare explicit scenarios side by side, seeing precisely which threshold or weight changed a flag. Retain a composite only as an optional illustrative output. Do not imply that the three presets are validated standards for entire classes of nonprofits.

### 7. Let the nonprofit supply financial context

Add optional notes on multi-year awards, restriction-release timing, planned reserve drawdowns, seasonal receipts, and major one-time expenditures. Attach them to the relevant indicator and export them with the report. Add two or three years of comparable data with an explicit fiscal-period length. These are proposed applicant-facing improvements, not claims about PJMF's current functionality. Context should accompany the calculation rather than silently adjust it.

### 8. Make existing controls behave as advertised

The organization-type selection is collected in the interface but is not used in runAnalysis. Either explain that it is descriptive or use it to suggest a scenario that the user explicitly confirms. Currency selection changes formatting only. State that all entries must use the same currency; do not imply conversion occurs. If actual conversion is later added, record the exchange rate, date, source, and rounding policy.

Use real label associations, keyboard-operable step navigation and profile selection, and explanations that can be opened without hovering. The current markup includes labels without for attributes and interactive divs without equivalent keyboard behavior. These are source-review findings; a full accessibility audit remains to be done.

### 9. Make reports reproducible and input handling safe

Include the application version, scenario settings, data completeness, sources, and creation date in downloads. Offer an explicit local export/import option so users can revisit a scenario without transmitting financial data to a service. Escape user-controlled text before inserting it into report HTML; the organization name is currently interpolated into a string assigned to innerHTML. This is a source-level concern, not a claim of a demonstrated external exploit.

### 10. Defer automated document extraction until the manual workflow is dependable

Document uploads could reduce retyping, but they add accuracy, confidentiality, and operating-cost obligations. A later version should extract values into a structured schema, cite the exact page, preserve uncertainty, and require user confirmation before deterministic calculations. Evaluate with representative statements and known answers. Keep the manual path available. Do not add an LLM simply to make the present AI labels technically true.

## Recommended implementation sequence

Preserve the live version as the historical baseline in the future repository. Fix items 1–5 and the scoring regressions first. Then implement scenario comparison, nonprofit context, and reproducible exports. Consider extraction only after users demonstrate that manual entry is the main remaining obstacle. Keep the source ledger and version history alongside the code so future changes can distinguish documented PJMF behavior from this tool's own design choices.
